## Contrato do host-check

Instruções completas no [README](../README.md). Executar exclusivamente no Arch host autorizado, com `COCKPIT_MODE=host`, `COCKPIT_HOST_CONFIRMED=yes`, base absoluta de projetos e CLI local no PATH.

O gate roda antes da chamada nativa em **todas as entradas do app** que alcançam o adapter. Requer Linux, ID exato `arch`, consentimento e ausência de marcadores conhecidos de guest; DMI desconhecido/vazio falha fechado. Não existe flag de bypass. Isso reduz erro operacional, mas não autentica bare metal: um guest que disfarce seus indicadores pode ser indistinguível. A instrução de operar diretamente no host e a conta confiável continuam necessárias.

Após o gate, uma única consulta `msb list --format json` usa argv fixo, stdin ignorado, timeout 3 s, saída limitada a 256 KiB por stream, SIGKILL somente do próprio subprocesso na falha e nenhum shell. O resultado é validado integralmente antes de persistir. Parser inválido: FAIL explícito, contagens null, banco anterior preservado. Não há comando de criação/controle de VM.

Projetos são filhos diretos válidos da base, sem seguir symlinks nem ler conteúdo. SQLite dedicado ao Cockpit recusa symlinks/arquivos estrangeiros; somente a observação integral bem-sucedida substitui o snapshot numa transação. O check fecha/reabre o banco e compara dados normalizados. HTTP usa esse mesmo snapshot capturado, não dispara novas consultas ao CLI; verifica health, API, assets, correlação e recusas de origem/query/mutação/path. Servidor temporário é encerrado no finally. Nenhuma porta de controle de VM é aberta.

Relatório: `PASS` para check exercitado com sucesso; `FAIL` para erro observado; `NOT_VERIFIED` para check não exercitado/incompleto. Exit codes: 0 para todos os checks automáticos obrigatórios, 1 para FAIL, 2 para obrigatórios incompletos. Navegador visual e versão do CLI são campos separados e ficam NOT_VERIFIED até evidência externa. Sem VM autorizada observada, `real_vm_presence` permanece NOT_VERIFIED. Um PASS automático não declara aceite visual/versão. Overrides de teste são sempre `source: synthetic`.

## Decisão e challenge resolvido

1. **Bootstrap circular / dois locks:** adotado pacote npm dedicado ao runtime, com pin exato e lock separado do Bun do app. Node/npm são pré-requisitos somente da instalação; quem já tem Bun correto pode instalar pelo lock e usar o launcher. Custo: manter dois locks de finalidades distintas, mais a dependência de teste Happy DOM. Evidência: bootstrap limpo, repetição offline e versão real conferida; instalador de distribuição Bun explicitamente documentado, scripts do app desabilitados.
2. **Arch não prova host:** consentimento/OS são filtros, não identidade física. Gate repetido no adapter, marcadores conhecidos e DMI desconhecido recusados; testes demonstram zero spawn nas recusas. Residual documentado, sem alegar isolamento autenticado. Próximo gatilho: evidência do ambiente real ou nova variante guest conhecida.
3. **Fixture não prova compatibilidade:** nenhuma fixture upstream foi promovida a amostra do operador. A busca em fontes primárias não forneceu uma amostra autenticada da instalação dele. Falha real de parser deve ser FAIL, nunca mascarada como NOT_VERIFIED ou inventário vazio. Próximo gatilho: saída sanitizada e versão do CLI no host.

## Falhas encontradas e corrigidas

Revisão independente confirmou F1 médio (Firecracker não detectado) e F2 baixo operacional (cancel de body HTTP já consumido). Ambos corrigidos pelo Tech Lead e revalidados pelo revisor: Firecracker/DMI ausente/vazio recusados antes do spawn; cancel apenas se body ainda não consumido. Uma execução subsequente identificou assertion antiga do fake de launcher após inclusão de `--no-env-file`; fake atualizado para verificar os dois argumentos. Suíte final integral aprovada. Histórico detalhado em [m0a1-security.md](m0a1-security.md).

Não há finding confirmado aberto nos casos exercitados. Isso não certifica ausência de vulnerabilidades. O Tech Lead revisou defensivamente as correções; a revisão adversarial limitou-se a fakes/fixtures locais, sem HTTP/VM real.

## Riscos, operação e propriedade

- DMI/heurísticas podem causar recusa conservadora em hosts incomuns e não provam host físico; sem bypass automático.
- CLI real pode usar formato não aceito, nomes não autorizados ou tabela decorada: falhar explicitamente e obter amostra antes de alterar parser.
- Conta/PATH/diretórios locais são confiáveis por contrato. Guard de Host/Origin não autentica processos locais. Não usar proxy/túnel/LAN.
- Checks de filesystem não são atômicos contra trocas concorrentes por outro escritor local adversarial. Risco residual herdado do M0a; rever antes de ampliar a fronteira de confiança.
- Logs JSON registram rota conhecida, IDs gerados, status, duração e código sanitizado; sem prompts, inventário ou saída crua. Traces são IDs de correlação locais, não spans/exportação distribuída verificados. Retenção de stdout cabe ao operador; banco mantém só snapshot atual.
- Operação: manter mock default; erro de discovery → conferir código/camada sem apagar SQLite ou reiniciar VMs. Em erro de parser, coletar amostra sanitizada no host; em erro de persistência, preservar banco e verificar permissões/espaço. SLI sugerido: sucesso e duração de requests válidas de discovery; baseline/SLO/alertas seguem pendentes. Encerrar somente o processo Cockpit.
- [Ownership Card](m0a1-ownership-card.md) e [ledger](m0a1-ownership-ledger.json): `explained`, sem confirmação de domínio humano. Card M0a anterior marcado `stale` diante do novo contrato.

UI de produção foi preservada e ganhou verificação comportamental.

Challenger, revisão e mentor foram acionados sob demanda; tokens/cache/custo/tempo por agente não foram medidos. Não inferir custo de assinatura ou zero.
